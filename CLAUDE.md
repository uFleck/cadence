# Cadence

Tauri 2 desktop app (React 19 + Vite, Rust backend, SQLite). It reads the English prompts the user wrote to Claude Code, scores how natural they sound with TypeSafe's Jev, coaches the worst ones with `claude -p`, and runs on its own every day at 22:00 local time.

## Layout

- `src/api.ts`: the IPC contract with the Rust commands and events. Change the Rust `model.rs` types and `api.ts` together.
- `src/App.tsx`: frameless window shell, nav, banners, status bar, and the refresh wiring (`messages-changed`, `run-progress`).
- `src/components/`: one view per file (`Today`, `MessageList`, `Patterns`, `SettingsView`), plus `MessageCard` (the rewrite-first card), `StatusBar`, `WindowControls`, `Dialog`, and `shared`.
- `src/components/Progress.tsx` and `Practice.tsx`: the first-draft trend, the recurring slips, and the Practice cards (retry and re-test). Backend in `src-tauri/src/progress.rs` and `retest.rs`.
- `src/components/Spending.tsx`: the spending dashboard (totals, 30-day chart, every Claude response). `src/drafts.ts` keeps an unsent version in `localStorage`, so leaving the card never loses it.
- `src/dev/mockBackend.ts`: stands in for Tauri when running `pnpm dev` in a plain browser. Keep it in step with `api.ts`.
- `src-tauri/src/`: `ingest` (Claude history and transcripts), `db` (SQLite), `jev` (TypeSafe client), `coach` (`claude -p`), `pipeline` (one run), `schedule` (22:00 slot logic), `lib` (commands, tray, scheduler).
- `src-tauri/src/interview.rs`: the Interview practice mode: built-in question bank, the `claude -p` feedback prompt and schema, and output parsing. It reuses `coach::run_claude`.
- `src/updater.ts` and `src/components/UpdateButton.tsx`: the in-app updater (status bar, packaged builds only). "Update to vX" opens an in-app panel with the release notes (`parseNotes` turns the `* commit` bullets into a list); never use a `title` tooltip for them. `?update-demo` in `pnpm dev` shows a made-up release to style it. `release.yml` builds and signs on a `v*` tag and uploads `latest.json`; the signing key is the `TAURI_SIGNING_PRIVATE_KEY` secret of the `Production` environment, and its public half is in `tauri.conf.json`.

## Rules

- **Never use native dialogs in the desktop app.** No `alert`, `confirm`, `prompt`, or `@tauri-apps/plugin-dialog`. Confirmations and errors use the in-app `Dialog`.
- **Never use native tooltips.** No `title` attribute on a DOM element and no `<title>` inside an SVG: the webview draws an unstyled pop-up for both. Put `data-tip="text"` on the element (HTML or SVG); the one `Tooltip` mounted in `App` shows it on hover and keyboard focus. A disabled button does not fire hover events, so put `data-tip` on a wrapper. Icon-only controls and chart marks still need an `aria-label`.
- **Every install uses its own TypeSafe key; none is ever bundled in the build, the repo or CI.** The user pastes it in Settings and `jev.rs` keeps it in the OS credential store (Windows Credential Manager, via `keyring`; a debug build uses a separate entry). The `TYPESAFE_API_KEY` environment variable is only the fallback (it is also what `jev_eval` uses when nothing is saved). Never write the key to a file, a log or the database, and never send it back to the UI: the frontend only learns its source (`app`, `env`, `none`).
- **Cadence must never ingest its own prompts.** The `claude -p` calls run in `<app data>/coach`, and ingestion skips every message whose `cwd` is under that folder. Keep both in step if either changes.
- Naturalness is always shown as a number next to the meter; colour is never the only signal.
- Run the app through Spawner (`spawner:tauri dev`), not a terminal.

## Data

- `messages` is deduped by a hash of the whitespace-normalised text, so a prompt present in both `history.jsonl` and a transcript is stored once.
- Ingestion tails each source file from a stored byte offset and only consumes complete lines.
- A run is idempotent: it only screens unscreened rows. It never coaches: `claude -p` runs only when the user writes a new version of a message, and it reviews that version (the original goes along as context). Coaching strips the stray `\"` the model sometimes writes (`coach::clean`).
- Every version the user writes is an `attempts` row with its own Jev `screen` and its own `coaching` (JSON). `Message.coaching` is always the review of the latest attempt; the `coaching` table only feeds the patterns. `MessageCard` owns no message data: the parent passes the message and gets every change back through `onChange` (it re-reads with `get_message`), so reopening a card shows what was saved.
- The coach is told to check whether a word is a noun or work term before "correcting" it (a 'lead' is a potential customer, not the verb), and to say in `Coaching.assumption` which reading it took. The user's own terms live in `kv('glossary')` (Settings, one `term: meaning` per line, capped at 2000 chars) and go into every `coach::ask` prompt as terms never to correct. No project folder or neighbouring messages are sent as context, on purpose.
- The queue is settled by the rewrite, not only by hand: `save_attempt` scores the new version, and reaching `Settings.flag_threshold` sets `reviewed_at`; falling short clears it, so a poorly rewritten message comes back (also from Reviewed). The queue orders by the latest version's score, falling back to the original's. "Mark reviewed" ("Done anyway" after a poor version) is the manual way out. An unscored version (no key, Jev down) changes nothing. The `rewritten` filter lists every message with at least one attempt.
- `ai_usage` records every AI call: `claude -p` calls (`coach`, `interview`) with the cost and tokens read from the JSON envelope (`coach::usage_from`; recorded before the answer is parsed, since a call that fails to parse still cost money), and one `screen` row per Jev call, priced at $0.042 per million input tokens (output is free). The Jev response carries no token count, so `jev::usage` estimates the input at about four characters per token over the whole request; treat that cost as an estimate, and replace it with the real count if the API ever returns one. `total_cost_usd` is the list-price equivalent, not a charge on a subscription. Spending from before this table existed is not counted.
- Ingestion redacts file paths and links (`redact.rs`): a path becomes its file name (`@src/x/Y.razor` becomes `Y.razor`) and a URL becomes its host (`https://github.com/o/r/pull/1` becomes `github.com`; written as "this github.com link" unless the user already put a determiner or a noun like "PR" around it). Different paths that share a file name within one message get numbered names (`S.cs`, `S2.cs`) so they do not read as "S.cs, S.cs and S.cs"; the same path always keeps the same name. Folders, queries and credentials are never stored or sent to Jev or `claude -p`. The stored text, word count, Jev score and coaching all use the redacted text; the message id still hashes the original. `Db::open` redacts rows stored earlier and drops their screen and coaching so the next run redoes them. `redact::VERSION` plus `kv('redaction')` trigger a one-time re-read of all sources when the redaction output changes, and `insert_messages` rewrites a stored row (dropping its screen and coaching, keeping attempts and the reviewed mark) when the redaction of its original now differs. Placeholder phrases such as "this file" clash with the surrounding grammar ("these this file files"), while a file name works like a proper noun in any position.
- A screen only counts when `english >= MIN_ENGLISH` and `prose >= MIN_PROSE` (`model.rs`; `db.rs` builds its SQL from them). `prose` asks Jev whether a person wrote sentences, so pasted logs, stack traces and code never reach the queue. Screens saved before `prose` existed have it NULL and are screened again on the next run.
- Jev's naturalness `score` is a probability-weighted mean of four levels, so it never reaches 3 on its own. The `is_native` yes/no question lifts a message to `TOP_SCORE` (3) when `native >= MIN_NATIVE`, Jev names no issue, and its own score is already `>= MIN_TOP_FROM` (`jev::with_top`). On its own, the yes/no answer also passes subtle mistakes (false friends, a blunt register), so the top only lifts messages that were not flagged anyway; the eval's top-score table compares rules on Jev's answers before the rule. The `slip` question looks for mistakes the score misses (false friends, word-for-word Portuguese, a blunt register); at `MIN_SLIP` confidence it caps the score at `SLIP_SCORE` (below the default goal) and names the issue when Jev named none (`jev::with_rules`). It is not stored; the eval's slip table shows what each confidence would catch and wrongly flag.
- `model::Issue::ASKED` is the issue set Jev and the coach pick from (articles, agreement_tense, typo, missing_word, preposition, awkward_phrasing, word_order, pt_calque, register). `grammar`, `preposition_collocation` and `word_choice` are only kept so stored rows read; the UI labels them "(older)". Renaming or splitting `issue` labels does not touch the scores, so it needs no `RUBRIC` bump (a bump hides the first-draft trend before it and re-screens rewritten messages); older rows keep their old label until a message is screened again.
- `model::RUBRIC` versions `questions()`; bump it whenever a change to them can move a score. Each screen stores its rubric (0 = before rubrics). Scores from different rubrics are never compared in the UI, and a run re-screens only the originals of rewritten messages whose rubric is old, never the whole table. Text the user writes (attempts, interview answers) reuses a stored screen of the identical text under the current rubric (`Db::known_screen`) instead of calling Jev. Score gaps under `SAME_SCORE` (0.1, `shared.tsx`) show as no change.
- **Retries are blind and capped, on purpose.** Writing the next version while the coach's last answer is on screen turns a rewrite into copying (it improves the revision, not the writing). So while the user writes a new try, no earlier review is shown or can be opened (`MessageCard` and the Practice retry card; scores stay visible), and there is no hint or peek control: do not add one. A message takes at most `MAX_TRIES` (3) versions (`save_attempt` refuses a fourth); the third settles the message whatever it scored, since no try is left to bring it back with.
- **Progress measures first drafts, not retried scores.** `Db::progress` (`progress.rs`) averages the screen of each message as first written, per local week, next to the newest scored version of the messages that were rewritten (`after_retries`). The retried score tends to sit near the top for anyone who retries until it passes, so it says little about what the user writes unaided; the first-draft trend is the learning signal. Only screens and attempts under the current `RUBRIC` count (scores of different rubrics are never compared), so after a `RUBRIC` bump the chart has only the weeks screened since; the UI says so. Slips are flagged messages per issue in the last 7 days against the 7 before.
- **Re-tests check transfer.** `Coaching.idea` is a plain-English sentence of what the message meant, written by the coach with the review of each version (no extra call). When a message settles and its newest review has an idea, `schedule_retest` adds a re-test `RETEST_FIRST_DAYS` (4) later; the user writes the message from the idea alone (the old text is never shown) and `save_retest` scores it (one Jev call, reusing a stored screen of identical text). Missing the goal on the first one brings a second after `RETEST_SECOND_DAYS` (10); "Later" moves one by a day. Messages coached before `idea` existed get no re-test. Every re-test answer costs one Jev call, so a message never has more than two.
- `interview_questions` holds the built-in bank (`interview.rs`, `custom = 0`) plus the user's own (`custom = 1`). `Db::open` re-seeds the bank with `INSERT OR IGNORE` on the unique text, so new bank questions appear on the next start. `interview_answers` cascades with its question; the Jev screen and the feedback are stored as JSON.

## Threshold eval

`src-tauri/evals/cases.json` holds 132 labelled messages (native, flawed, pasted, Portuguese, some with paths that go through `redact`, and `agent-*` prompts written the way people talk to a coding agent: no final period, lowercase, quoted tool names like `just`). `cargo test --lib jev_eval -- --ignored --nocapture` screens them with the real TypeSafe API (needs `TYPESAFE_API_KEY`, costs cents) and asserts the English, prose and flag thresholds sit well inside the gaps between the groups. Re-run it after touching `questions()` in `jev.rs` (and bump `RUBRIC`) or any threshold, including `MIN_NATIVE`.

**Never run the eval, or anything else that calls Jev, on your own.** The database holds 1000+ messages and every Jev call costs money. Agents and delegated briefs use free checks only (`cargo test --lib`); when a change needs the eval, say so at the end and let the user run it or ask for it. Changes that alter stored text must re-screen only the rows they affect (as `insert_messages` does), never the whole table.
